# ML Agent v0.2 — проект интерфейса и безопасной интеграции

**Проект:** CPS-PredDiag. **Версия документа:** 0.1, 06.11.2026.
**Состояние:** проект интерфейса и отдельный *неинтегрированный* исследовательский прототип `ml_agent_v02.py`. Интеграция с Coordinator, Streamlit, моделями CatBoost и производственной базой данных **не выполнена**.

## 1. Состояние текущего кода (проверено по доступным копиям исходных модулей)

`ml_agent.py` содержит исследовательский `MLAgent`, который:

- требует `transition_102_confirmed=True` от внешнего компонента;
- по манифесту допускает **только горизонт 15 минут** и class 2;
- извлекает 12 признаков из последних 300 секунд и считает оценку некалиброванной;
- загружает локальный `joblib`-артефакт и не подключен к Coordinator.

`coordinator.py` содержит `coordinate_decision(rule_summary, predictions)` и объединяет Rule-Based + Prognostic через состояния порогов, **не получая ML-score**. Предыдущий `MLAgent` нельзя просто подменять CatBoost-30 и считать сохраненным контракт системы.

Точный текущий код на компьютере разработчика необходимо сверить перед внедрением: доступны файлы из ранее переданных материалов, а не прямой доступ к актуальной рабочей папке `D:\CPS-PredDiag`.

## 2. Назначение v0.2

Отдельный автономный диагностический модуль, вычисляющий **некалиброванный score** появления class 2 в следующие 30 минут по прошлой телеметрии **без oracle `102`**, с указанием статуса пригодности данных и версии модели. Не определяет физическое состояние скважины и не выдает управляющих команд оборудованию.

Приоритет внедрения: **shadow mode**. Модуль может формировать независимые рекомендации для анализа и сохранения истории, но не меняет `decision_level` / `action` существующего Coordinator и не вмешивается в исполнительные цепи.

## 3. Компоненты и поток данных

```text
Входные данные WELL/телеметрия (только прошлое по времени t)
    |
    v
[Контроль времени / 900 с непрерывной истории / качество датчиков]
    |        \--> [insufficient_data / invalid_time]
    v
[Извлечение фиксированной схемы 12 признаков из последних 300 с]
    |
    v
[Версионированная CatBoost-модель / score]
    |
    v
[Политика тревог: порог + подтверждения + состояние по well_id]
    |
    v
[Shadow-result: результат + происхождение + объяснение ограничений]
    |                            \--> [CSV/JSONL или БД позднее]
    v
[Отдельный наблюдатель/адаптер для UI, без влияния на Coordinator]

Существующий pipeline:
Rule-Based Agent + Prognostic Agent --> Coordinator --> Explanation --> Streamlit
                                ^
                    ПОКА НЕ ПЕРЕДАВАТЬ ML как аргумент
```

## 4. Минимальный контракт данных (проект)

**Вход:** `pd.DataFrame` с `DatetimeIndex`, строго возрастающим с шагом 1 секунда, содержащий последние 900 секунд истории на момент `decision_time`. Только реальные доступные датчики. Поля `class`, `state`, `event_time` могут присутствовать в исходном offline-датасете, но **отбрасываются до вызова извлечения признаков**. `well_id` — ключ состояния и аудита, не признак модели.

**Прототип API:** в коде используется класс `ShadowMLAgentV02` и обязательный `ShadowConfig(model_version, threshold, confirmations)`; модель передается явно, без загрузки артефакта из файловой системы.

```python
from ml_agent_v02 import ShadowConfig, ShadowMLAgentV02

agent = ShadowMLAgentV02(
    model=trusted_model_or_none,
    config=ShadowConfig(model_version="research-v0", threshold=0.5, confirmations=2),
)
result = agent.predict(
    history=history_until_t,
    well_id="WELL-00012",
    decision_time=t,
)
```

**Выход:** словарь или типизированный объект со стабильными полями:

| Поле | Тип | Семантика |
|---|---|---|
| `agent` | str | `ml` |
| `protocol_version` | str | Версия API, например `0.2` |
| `model_version`, `artifact_sha256` | str / null | Версия и хэш модели; `null`, если модель недоступна |
| `status` | str | `experimental_prediction`, `insufficient_data`, `invalid_time`, `model_unavailable`, `model_error` |
| `well_id`, `decision_time` | str | Скважина и время принятия решения |
| `event_class` | int | 2 |
| `horizon_minutes` | int | 30 |
| `model_score` | float / null | Конечное число в `[0,1]` лишь при успешном прогнозе; **не калиброванная вероятность физического отказа** |
| `uncalibrated` | bool | `true` до независимой калибровки |
| `sensor_coverage` | dict | Доля конечных измерений основных датчиков |
| `threshold`, `confirmations` | float/int / null | Предварительно заданная исследовательская политика |
| `alarm_active`, `alarm_new_start` | bool / null | Состояние и факт нового начала тревоги, если политика применена |
| `reason` | str / null | Причина пропуска/ошибки; не маскировать причину нулевым score |
| `shadow_mode` | bool | Всегда `true` в v0.2 |

`status != experimental_prediction` означает, что score отсутствует (`null`), **а не равен нулю**. Поля `class`, `state`, oracle-флаги и future labels не входят в API.

## 5. Инварианты вычисления

- История строго до `t` включительно; 900 последовательных секунд. При нарушении — статус `invalid_time`/`insufficient_data`, а не прогноз по упорядоченной задним числом истории.
- Ровно 12 признаков базовой версии в **том же порядке и с теми же формулами**, что и в обучении. Сверять по манифесту.
- Наличие минимум двух основных датчиков с покрытием 90% на рабочем 300-секундном отрезке.
- Обязательный `well_id`, но без подачи в CatBoost. Статистика датчиков и нормировка не могут опираться на знания об изучаемой скважине из будущего/других сегментов теста.
- Любая новая схема признаков (H1/H2) требует собственного `feature_schema_version`, отдельной модели и повторной проверки, но не скрытого изменения в том же v0.2-артефакте.
- Порог и подтверждения задаются в неизменяемом проверенном манифесте. Запрещено хранить единственный «универсальный порог 0,5» как гарантированно лучший.
- Повторный вызов с тем же `(well_id, decision_time)` должен быть идемпотентным: не создавать второй счетчик подтверждений и второе начало тревоги.
- При разрыве во времени/переключении WELL состояние последовательных подтверждений сбрасывается; истечение предупреждения и сброс на недостаточных данных должны быть явно документированы.

## 6. Политика ошибок и безопасности

- Не загружать недоверенные `joblib` / pickle-артефакты; проверять имя, хэш и схему доверенного локального манифеста до `joblib.load`, где это возможно.
- Внутренняя ошибка модели -> `model_error` + диагностическая запись; не подменять score нулем и не влиять на Coordinator.
- Отсутствие модели -> `model_unavailable`; это штатный статус тестового прототипа.
- Все выходы содержат `shadow_mode=true` и запрет на самостоятельное управление оборудованием.
- Не отображать `model_score` как «вероятность отказа 70%» до корректной калибровки и ее проверки на независимых данных.

## 7. План модульной разработки (без правки рабочего приложения на первом шаге)

1. **Проверка актуальной локальной версии кода:** сравнить `ml_agent.py`, `diagnostic_pipeline.py`, `coordinator.py` и тесты с исходниками, использованными при проектировании (это остается обязательным перед интеграцией).
2. **Выполнено в отдельном прототипе:** `ml_agent_v02.py` с `ShadowConfig`, 30-минутным контрактом и отсутствием oracle-условия `102`; переиспользуется featurizer из старого `ml_agent.py`.
3. **Выполнено на синтетике:** `tests/test_ml_agent_v02.py` проверяет отсутствие будущего/label leak, время, непрерывность 900 с, сообщения при ошибках, policy и изоляцию состояния.
4. **Не выполнено:** привязка к доверенному экспортированному CatBoost-30 и сверка реальных OOF при одинаковом model artifact, входных окнах и политике.
5. **Не выполнено:** отдельный *observer*, который читает результаты и формирует объяснение, не меняя контракт `coordinate_decision()`.
6. **Отложено:** UI и PostgreSQL; любое влияние на `action` Coordinator требует отдельного исследовательского решения и тестов.

## 8. Минимальные приемочные проверки прототипа

- При одинаковых входах, модели и начальном состоянии replay выдает тот же результат, версии/хэши сохранены.
- Замена строк после `t`, замена `class`/`state` не меняют модельного score.
- Ошибки истории, отсутствующие два из трех датчиков, отсутствие модели, повтор времени, переплетение WELL -> контролируемые статусы и корректное состояние policy.
- При отключенном shadow-observer поведение Coordinator совпадает с прежним побайтно/семантически в тестовых фикстурах.
- В отчетах различаются `active`, `new_start`, счетчик подтверждений, событие `2` и переходная фаза `102`.
- Никаких изменений production/UI до одобрения протокола и результатов тестов.

## 9. Статус решения о модели

CatBoost-12, горизонт 30 мин, hard negatives 25% — **перспективная исследовательская конфигурация**, но она не имеет независимого подтверждения превосходства. Строго вложенно выбранный вариант обеспечил обнаружение 9/11 при снижении активности тревог на контрольных данных ценой ухудшения оконной метрики F1. В v0.2 должен существовать режим **без обученного/утвержденного артефакта** с явным статусом `model_unavailable`. Не подставлять исследовательскую модель по умолчанию под видом готовой к эксплуатации.

## 10. Граница текущего прототипа

Тесты для `ml_agent_v02.py` используют подставной объект с `predict_proba`, а **не обученный CatBoost**. Они подтверждают только работу контракта в синтетических случаях, а не метрики качества на Petrobras. `artifact_sha256` в `ShadowConfig` проверяется лишь на формат: прототип **не вычисляет и не сверяет** хэш фактического файла модели. Перед реальной загрузкой нужен отдельный доверенный загрузчик и проверка manifest.
