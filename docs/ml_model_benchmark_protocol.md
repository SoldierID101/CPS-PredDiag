# Протокол: сравнительный анализ ML-алгоритмов для DHSV (v0.1)

## Исследовательский вопрос

Изменяет ли выбор классификатора качество ранжирования будущего риска DHSV
при неизменных признаках, горизонте и группах обучающих/тестовых скважин?

## Предварительно фиксируемые условия

- Источник: Petrobras 3W v2.0.0; подготовленный `cohort_features.csv`.
- Цель: наступление класса `2` в течение следующих 30 минут. НЕ RUL.
- Пригодная когорта: 503 окна / 66 положительных, 7 WELL / 11 эпизодов
  в уже изученной выборке.
- Признаки: 12 = 3 датчика × mean/std/delta/slope, вычисленные из прошлого.
- Частота диагностики: 5 минут. Входы `class`, `state`, `target`, будущие
  измерения и `event_time` запрещены как признаки.
- Внешние складки: LOOW по всему WELL — исключаем все записи тестовой скважины
  из обучения, включая другие файлы этой же скважины.
- Алгоритмы: Dummy prior, Logistic Regression, Random Forest, CatBoost, LightGBM.
- Гиперпараметры фиксированы в исходном коде **до просмотра результатов benchmark**;
  автоматически не подбираются по тестовой WELL.
- LR и RF получают заполнение пропусков медианами, рассчитанными **только
  на обучающей части** (дополнительно индикаторы пропусков). CatBoost и
  LightGBM обрабатывают пропуски сами.
- Основной показатель: AP/PR-AUC по объединённым out-of-fold прогнозам.
  Дополнительно ROC-AUC, Precision/Recall/F1 при 0,5 и обнаруженные эпизоды
  при 0,5. Метрики по скважинам публикуются отдельно.
- Бинарная метрика при 0,5 — только диагностика поведения. Для честного
  сравнения тревог пороги позже выбираются во внутренних LOOW складках
  с явными ограничениями на частоту ошибочных тревог.
- Нельзя выбирать итоговую модель по этим семи скважинам и объявлять
  полученное качество «независимым» из-за уже проведённых исследований.

## Ограничения

- 11 эпизодов: высокая дисперсия оценки событий; временные окна коррелированы.
- Используемая когорта сформирована ретроспективно с учётом разметки;
  сегменты вне неё не оцениваются как достоверно отрицательные.
- Контролей классов 0, 1, 3–9 в этом benchmark нет; специфичность
  на остальных типах событий будет проверяться отдельно.
- Групповая LOOW предотвращает прямую утечку записей одной WELL между train/test,
  но не устраняет многократную исследовательскую адаптацию к семи WELL.
- Вероятности моделей не откалиброваны для трактовки как физической
  вероятности будущего отказа.

## Что делать после benchmark

1. Проанализировать AP и нестабильность по WELL, а не только итоговый рейтинг.
2. Прежде чем выбирать «победителя», зафиксировать вложенную процедуру
   выбора порога и сравнить политику предупреждений на контролях других классов.
3. Отдельно сформулировать и проверить гипотезы новых признаков
   (относительные изменения, P-PDG), без подбора по WELL-00012.
4. После этого обсуждать Shadow Integration в Coordinator.
