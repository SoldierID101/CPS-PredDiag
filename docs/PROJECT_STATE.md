# CPS-PredDiag — паспорт текущего состояния проекта

**Состояние на:** 19 ноября 2026 года
**Назначение:** единая точка входа в архитектуру и текущую стадию НИР «Разработка метода предсказательной диагностики для управления киберфизической системой».
**Статус документа:** аудит **восьми** фактически предоставленных исходных файлов (`ml_agent.py`, `ml_agent_v02.py`, `diagnostic_pipeline.py`, `coordinator.py`, `explanation.py`, `experiments/replay_pipeline.py`, `rule_based_agent.py`, `prognostic_agent.py`), ранее предоставленного списка Git и отчётов. Не заменяет аудит конфигурации правил, Streamlit, тестов и БД.

## 1. Краткий итог

- Существует **исследовательский диагностический конвейер v0.1**: Rule-Based Agent, Prognostic Agent, ML Agent v0.1, Coordinator и Explanation. Старый ML Agent оценивает событие DHSV класса 2 на горизонте **15 минут только при внешнем подтверждении состояния 102**. Rule-Based Agent требует обоснованных порогов; Prognostic Agent экстраполирует тренды датчиков до порогов и не прогнозирует само событие отказа.
- Отдельно существует **Shadow ML Agent v0.2** с прогнозным горизонтом **30 минут без oracle-gating по состоянию 102**, допуском по **900 секундам непрерывной истории** и признаками по последним **300 секундам**. Он **ещё не подключён** к `DiagnosticPipeline`, `Coordinator` или Streamlit.
- Предыдущие пользовательские запуски подтвердили **221/221 тестов** и техническую эквивалентность нового shadow-агента с исследовательским CatBoost на **503/503 сопоставимых решений**, полученных из **22 файлов семи скважин**. Это **не независимая проверка прогностической эффективности**.
- Следующее действие по организации проекта: **использовать `docs/EXPERIMENT_REGISTRY.md` и `docs/DECISIONS.md` как общий индекс доказательств и решений**. Перед shadow-интеграцией осталось проверить фактическую конфигурацию `rules/class2_dhsv.json`, загрузчик правил, соответствующие тесты и нужные точки входа Streamlit; затем планировать тонкий адаптер, без изменения действий Coordinator.

## 3. Подтверждённая схема взаимодействия

```text
История показаний (DataFrame с DatetimeIndex)
    │
    ▼
DiagnosticPipeline v0.1
    ├─ ограничивает историю моментом решения, удаляет перечисленные поля разметки
    ├─ RuleBasedAgent.evaluate(последний снимок) ─────────────┐
    ├─ PrognosticAgent.predict(наблюдаемая история) ───────────┤
    └─ MLAgent v0.1.predict(история, transition_102_confirmed) ┤
                                                               ▼
                                                     coordinate_decision()
                                                               │
                                                               ▼
                                                     generate_explanation()
                                                               │
                                                               ▼
                                                  Результат исследования

ShadowMLAgentV02 — ОТДЕЛЬНАЯ ВЕТКА:
    история + well_id + decision_time → 12 признаков → модель → alarm_active/new_start
    Проверен offline replay, но не подключён к схеме выше.
```

`explanation.py` преобразует результаты Coordinator и агентов в русскоязычный текст. `experiments/replay_pipeline.py` последовательно вызывает **старый** `DiagnosticPipeline`, записывает `decisions.jsonl`, `timeline.csv`, `summary.json` и не подсчитывает Precision/Recall.

`coordinator.py` **не управляет оборудованием**. Приоритеты устанавливаются по результатам Rule-Based Agent и Prognostic Agent. ML-сигнал хранится как исследовательская информация и не переводит решение в `warning`/`critical` самостоятельно. Если проверенных показаний недостаточно, решение `unknown`, не `normal`.

### Уточнение по базовым диагностическим агентам (код проверен 19.11.2026)

| Компонент | Реальный вход | Параметры и проверки | Реальный выход / интерпретация |
|---|---|---|---|
| `RuleBasedAgent` | `evaluate(snapshot)` — **один текущий снимок**, словарь значений датчиков | Явные правила с `id`, `sensor`, `condition` (`>`, `>=`, `<`, `<=`), численным `threshold`, `severity`, `unit`, `source`, `message`. Проверка конечности порога и обязательности строковых полей | Словарь со `status`, `critical_count`, `warning_count`, `triggered_rules`, `complete` и перечнем недоступных правил. При пустом наборе правил — **`unknown`**, не `normal` |
| `PrognosticAgent` | `predict(history, decision_time=None)` — временной ряд | По умолчанию горизонт **15 минут**; последний участок **300 последовательных секунд**, покрытие датчика ≥90%, последнее значение существует. Настраиваемые пороги для `P-PDG`, `P-TPT`, `P-MON-CKP`, `T-TPT` | Список результатов по каждому порогу: `already_exceeded`, `predicted_crossing`, `no_forecast` либо `insufficient_data`; при отсутствии порогов — **пустой список** |

**Важные различия:** Rule-Based Agent — диагностика **текущего** состояния по физическим условиям. Prognostic Agent — прогноз **пересечения численного порога датчика** по линейному тренду, **не время до отказа** и не предсказание метки DHSV класса 2. ML Agent v0.2 — отдельный прогноз возможного события класса 2 в следующие 30 минут. Их результаты нельзя представлять как одну и ту же вероятность неисправности.

**Приоритеты Rule-Based:** `critical` выше `warning`; если ни одно правило не сработало, но хотя бы одно измерение недоступно, возвращается `unknown`; `normal` допустим только при ненулевом полном наборе проверенных правил. Если правило сработало, но другие данные отсутствуют, статус предупреждения/критичности сохраняется, а `complete` остаётся `false`.

**Приоритеты Coordinator:** критическое правило или уже превышенный критический порог → `critical`; прогноз пересечения физического порога или предупреждающее правило → `warning`; `normal` только при подтверждённом `normal` от Rule-Based; иначе `unknown`. ML-оценка не меняет автоматически действие Coordinator. При **пустых правилах и пустых прогностических порогах** оба диагностических компонента не подтверждают норму, и Coordinator возвращает `unknown` — это корректное безопасное поведение, а не ошибка теста. **Как именно сконфигурированы реальные правила в локальном проекте, пока не проверено.**

## 4. Контракты двух ML Agent

| Свойство | `ml_agent.py` (v0.1) | `ml_agent_v02.py` (v0.2 / shadow) |
|---|---|---|
| Входной метод | `predict(history, transition_102_confirmed, decision_time=None)` | `predict(history, well_id, decision_time)` |
| Горизонт DHSV | 15 минут | 30 минут |
| Условие запуска | Внешнее подтверждение `class=102` | Состояние `102` не требуется |
| Длина анализа датчиков | 300 секунд | 300 секунд, после допуска 900 секунд |
| Датчики | `P-MON-CKP`, `P-TPT`, `T-TPT` | Те же; экстрактор импортируется из `ml_agent.py` |
| Признаки | 12: mean / std / delta / slope_per_hour | Те же 12 в том же порядке |
| Требование к датчикам | Минимум 2 из 3, покрытие ≥90% на используемом окне | Такое же |
| Модель | Загружается из доверенного локального joblib при создании объекта | Передаётся готовым объектом в конструктор; отсутствует автозагрузка |
| Выход тревоги | `above_research_threshold` (при 0,5) | `alarm_active`, `alarm_new_start`, настраиваемый порог, 1–2 подтверждения |
| Хранение состояния | Нет последовательной политики подтверждений | Состояние по `well_id`; `reset()` для границ replay |
| Применение | Старый `DiagnosticPipeline` | Отдельные offline replay / исследования |

**Внимание:** `model_score` в обеих реализациях не калиброван и не должен интерпретироваться как физическая вероятность отказа. Ни одна из реализаций не вычисляет достоверное время до отказа.

## 5. Технические несовместимости — подтверждены чтением кода

### B1. Сигнатура вызова ML Agent

`DiagnosticPipeline.run()` вызывает:

```python
ml_agent.predict(observed,
                 transition_102_confirmed=...,
                 decision_time=moment)
```

`ShadowMLAgentV02.predict()` требует обязательный `well_id` и **не принимает** `transition_102_confirmed`. Прямое подставление v0.2 вместо старого агента приведёт к ошибке вызова. Нужен отдельный адаптер/режим конвейера, не замена существующего агента без тестов.

### B2. Интерпретация результата Coordinator

`coordinate_decision()` признаёт старый ML-сигнал только когда `status == 'experimental_prediction'` и `above_research_threshold is True`. В выходе v0.2 **нет** поля `above_research_threshold`: есть `alarm_active` и `alarm_new_start`. Даже после решения B1 Coordinator не распознает положительный v0.2-сигнал по прежнему правилу и может ошибочно написать «ниже порога 0.5». Разные модельные пороги также требуют устранить жёстко зашитое `0.5` в исследовательских сообщениях.

### B3. Пропускная способность и время

v0.2 проверяет 900 непрерывных секунд до момента решения, а **шаг 300 секунд учитывает при сбросе последовательности подтверждений**, но не запрещает любой отдельный вызов в другой момент. Периодический график решений обеспечивает вызывающий replay-скрипт/адаптер. Между файлами той же скважины требуется `reset(well_id)`.

### B4. Ограничения аудита данных

`DiagnosticPipeline` отбрасывает конкретный список полей разметки (`class`, `state`, `target`, `target_h15`, `event_class`, `label`), а не использует общую белую схему сенсорных полей. `ShadowMLAgentV02` внутри дополнительно ограничивает признаки тремя известными сенсорами, но при будущей интеграции полезно проверить, какие столбцы видят Rule-Based и Prognostic Agent. Это **пункт для аудита**, не установленная утечка.

### B5. Общая зависимость экстрактора

v0.2 импортирует `features_from_history`, `FEATURES`, `SENSORS`, `MIN_COVERAGE` из `ml_agent.py`. В `ml_agent.py` проверка временного индекса напрямую обращается к `.asi8`, предполагая наносекунды. v0.2 передаёт окну индекс `as_unit('ns')`, поэтому известная ошибка pandas 3.1.0 в нём устранена. Изменять общий экстрактор следует только с регрессионными тестами обеих версий.

### B6. Explanation ошибочно описал бы прогноз v0.2 как условный по 102

`generate_explanation()` при `status == 'experimental_prediction'` **безусловно** пишет «для случая подтверждённого переходного состояния 102». Это корректно для старого ML Agent, но **некорректно для v0.2**, который не использует метку 102. При будущей интеграции нельзя просто передать словарь v0.2 в старый Explanation: нужен отдельный режим/формулировки по `protocol_version` и тест на отсутствие ложного утверждения о 102. Также метод ориентируется на `decision.ml_research_alert`, а не `alarm_active`/`alarm_new_start`.

### B7. Старый replay не является replay ML Agent v0.2

`experiments/replay_pipeline.py` импортирует только `from ml_agent import MLAgent` и создаёт `MLAgent(args.model_dir)`. `iter_decision_positions()` начинает решения после **300** подряд идущих отсчётов и по умолчанию повторяет их каждые **300 секунд**, тогда как v0.2 требует **900 секунд** непрерывной истории для допуска. В `timeline_row()` сохраняются `ml_above_research_threshold`, но **нет** `well_id`, `alarm_active`, `alarm_new_start`, `artifact_sha256`, `reason`. Для v0.2 уже существуют **отдельные** `offline_replay_ml_v02*.py`; старый replay не нужно менять ради их научной проверки.

### B8. Граница проверки «нет будущего»

`replay_pipeline()` передаёт `pipeline.run()` только префикс `frame.iloc[:pos+1]`; `DiagnosticPipeline.run()` дополнительно обрезает по моменту решения и удаляет указанные поля разметки. При `oracle_replay` для старой модели допускается использование только прошедших 300 секунд метки 102, что **не является независимой диагностикой**. В обычном `blind` это подтверждение не формируется. Не смешивать `oracle_replay` с результатами blind-исследования 30-минутного горизонта.

### B9. Проверка источников физических порогов — пока только формальная

Оба агента требуют непустые `source` и `unit`, а также конечный численный порог. **Они не проверяют автоматически**, что указанный источник действительно обосновывает численное значение или что единицы измерения соответствуют колонке Petrobras. Настоящая проверка физического смысла должна выполняться при утверждении `rules/class2_dhsv.json` и конфигурации Prognostic Agent. Наличие строки `source` в JSON само по себе не означает валидации порога.

### B10. Ограничения простого Prognostic Agent

Экстраполяция строится по последним 300 секундам через линейный тренд; вычисляемый `trend_r2` записывается как диагностический атрибут, но **не используется как критерий допуска прогноза**. Нет доверительного интервала для времени пересечения, проверки устойчивости тренда на других интервалах, модели будущего отказа либо независимой промышленной валидации. Это ограничения прототипа, а не подтверждённые полевые ошибки.

### B11. Защита от попадания разметки в правила

`RuleBasedAgent` запрещает поле `class` / `state` по точному совпадению регистра; в его собственном конфигураторе, например, `Class` не попадает в список запрещённых имён. В `DiagnosticPipeline` поля меток отбрасываются независимо от регистра, что защищает штатный путь при известном списке названий. **Перед любой прямой оценкой правил вне Pipeline** следует добавить регистронезависимую проверку запрещённых имён и соответствующий тест. Это потенциальная поверхность утечки при нестандартном подключении, **не обнаруженная утечка в выполненных экспериментах**.

### B12. Фактическая конфигурация Rule-Based для DHSV — проверена 19.11.2026

Считаны текущие `rule_config.py` и `rules/class2_dhsv.json` (отдельно присланные исходники). В JSON указаны `schema_version: 1`, `dataset: Petrobras 3W Dataset v2.0.0`, `event_class: 2`, `approval_status: draft` и `rules: []`. Загрузчик допускает пустую конфигурацию и запрещает **непустые** правила без `approval_status == "approved"`. Правила проверяются через существующий `RuleBasedAgent`, но научная достоверность порогов и единиц измерения автоматически не устанавливается.

Локально по присланным файлам проверено: `load_rule_config(..., expected_event_class=2)` успешно загружает JSON, `load_rule_agent(...)` создаёт агент с нулём правил, `evaluate(...)` возвращает **`status: unknown`**, даже если переданы численные показания датчиков. Это правильная безопасная семантика, а **не признак отказа программного компонента**.

При создании старого replay `PrognosticAgent()` тоже не имеет порогов по умолчанию и возвращает `[]`. В штатном `blind` старый ML Agent не получает независимого подтверждения 102, поэтому его результат — `not_applicable`. При такой комбинации и отсутствии дополнительных конфигураций Coordinator возвращает `unknown` / `no_automatic_action`. Это **следствие проверенных контрактов**, не новый end-to-end прогон приложения.

### B13. Пределы утверждения правил

`approval_status == "approved"` является формальной отметкой оператора конфигурации, а **не доказательством** корректности численных порогов. Код загрузчика проверяет допустимые поля JSON, класс события, типы и наличие строк `source`/`unit` через `RuleBasedAgent`, но не проверяет внешний источник, совместимость единиц с конкретной скважиной или клиническую/физическую пригодность порогов. Переход от `draft` к `approved` без проверяемого обоснования **не предпринимать**.
