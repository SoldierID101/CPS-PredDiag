# Prognostic Agent v0.1 — границы применимости

**CPS-PredDiag · 28.10.2026 · исследовательский прототип**

## Назначение

`prognostic_agent.py` прогнозирует **время до достижения заданного диагностического
порога измеряемого параметра**, если его недавний линейный тренд сохранится.
Это **не время до физического отказа** и не вероятность неисправности.

Агент не использует PostgreSQL, целевые метки `class/state`, будущие измерения,
не взаимодействует с оборудованием и передаёт результаты в
`coordinator.coordinate_decision(predictions=...)`.

## Вход и расчёты

- История: `pandas.DataFrame`, индекс `DatetimeIndex`, измерения с шагом 1 с.
- Окно: последние 300 секунд, включая момент принятия решения.
- Качество сигнала: не менее 90% конечных значений; последний отсчёт обязателен.
  90% — **техническая настройка допустимости входных данных**, не
  диагностический порог, описанный в источнике.
- Метод: линейная регрессия `y(t) = a*t + b` по доступным точкам.
- Экстраполяция: до настраиваемого горизонта, по умолчанию 15 минут.
  Этот горизонт — **исследовательский**, а не подтверждённый параметр безопасности.
- `trend_r2`: описательная характеристика прямолинейности ряда,
  сама по себе **не калибрует достоверность прогноза**.

Текущий API допускает сигналы `P-PDG`, `P-TPT`, `P-MON-CKP`, `T-TPT`.
Расширять список после проверки единиц и данных.

## Обязательное условие: внешнее обоснование порога

Агент **по умолчанию не содержит ни одного правила**. Без переданных порогов
`PrognosticAgent().predict(history)` возвращает пустой список.

Для каждого порога требуется:

| Поле | Смысл |
|---|---|
| `id` | Уникальный идентификатор |
| `sensor` | Физический канал измерения |
| `threshold` | Число с доказанным происхождением |
| `direction` | `above` или `below` |
| `severity` | `warning` или `critical` |
| `unit` | Единица измерения порога |
| `source` | Проверяемый источник **самого численного порога** |

**Недостаточно** сослаться на статью Petrobras, которая описывает только
направление изменения давления: такая ссылка не подтверждает выбранную
абсолютную границу.

## Выходной контракт

| `forecast_status` | Значение |
|---|---|
| `predicted_crossing` | При сохранении тренда заданный порог достигается в пределах горизонта |
| `already_exceeded` | Текущее наблюдаемое значение уже по опасную сторону заданной границы |
| `no_forecast` | Пересечение в пределах горизонта не обнаружено; **не означает безопасности** |
| `insufficient_data` | Данные недоступны, есть пропуски времени или не выполнены требования качества |

В режиме `predicted_crossing` доступно `time_to_threshold_h`, а также
`trend_slope_per_hour`, `trend_r2` и покрытие датчика.

## Что проверено, а что нет

**Проверено на искусственных временных рядах:** вычисление наклона и времени
пересечения, отсутствие будущих измерений, микросекундный индекс, обработка
пропусков, отсутствие прав на использование `class/state`, взаимодействие с
Coordinator. **13 новых unit-тестов прошли локально.**

**Не проверено:** точность прогнозирования пороговых пересечений на реальных
скважинах, устойчивость при нелинейных режимах, частота ложных предупреждений,
применимость конкретных порогов. Никакие численные пороги Petrobras в модуль
не зашиты. До эмпирической проверки результаты — только исследовательские.

## Следующий этап

1. Составить реестр доступных физических/эксплуатационных порогов и их источников.
2. Выбрать порог **только при доказанном происхождении**; иначе оставить агент
   без порогов и задокументировать ограничение данных.
3. На историческом воспроизведении проверить качество предсказания
   **пересечения порога**, отдельно от распознавания класса DHSV и ML-прогноза.
4. Только после этих проверок обсуждать статус предупреждений и объединение
   результатов агентов.
